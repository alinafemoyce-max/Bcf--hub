# WoodmillFlow

**Digital Material Requests & Job Tracking. From request to collection, all in one place.**

WoodmillFlow is an **independent concept demonstration**. It shows how woodmill cutting requests could move from paper forms to a QR-code-accessible digital request, with a shared work queue for the woodmill operator.

> **Status: proof of concept.** WoodmillFlow is not an official, approved or endorsed Sunseeker International system. It is not connected to any company system. All names, clock numbers, production lines and orders are fictional.

## What it does

| Area | Features |
| --- | --- |
| **Employee request form** (`/request`) | **Section A, employee:** clock number (configurable rule), name, department or shed, production line, optional hull reference. **Section B, order:** the reference, date and time are generated by the server; optional date required; Normal or Urgent (Urgent needs a reason); instructions. **Section C, cutting items:** add, duplicate, edit and remove items. Each item has a material category, a description from a sample catalogue (or free text), thickness, length, width, quantity, grain direction, cutting and machining requirements, a drawing reference and notes. **Section D, review:** a full summary before you submit. |
| **Confirmation** | Order reference (`WM-2026-0019`), UK date (DD/MM/YYYY) and time (HH:mm, 24-hour), status, and a private tracking link. Buttons: Track, Submit Another, Copy Reference. |
| **Tracking** (`/track/<token>`) | Status timeline (Submitted → Accepted → In Progress → Ready for Collection → Collected) with the time of each step. Shows a ready-for-collection message and messages from the woodmill. You can reply to a clarification request and cancel before work starts. The page refreshes itself every 5 seconds and also has a Refresh button. |
| **My Requests** (`/requests`) | Requests submitted from this device. In demo mode it also shows Alex Taylor's sample requests. |
| **Operator work queue** (`/operator`) | Summary cards: New, Awaiting Clarification, Accepted, In Progress, Ready, Completed. Search and status filters. Orders are sorted by agreed priority, then oldest first. A notice appears when a new request arrives. On a laptop the queue and the order details sit side by side; on a phone they are separate screens. |
| **Operator actions** | Accept, Request Clarification, Start Cutting, Mark Ready for Collection, Mark Collected, Reject, Cancel. Reject, clarification and cancel require a message; Mark Collected asks for confirmation. Operators can add comments, either visible to the requester or internal. They also set the agreed priority (Normal, High or Urgent), which the requester's urgency request does not override. Every change is saved with the time and the operator, and appears in a status history. |
| **QR code** (`/qr`, `/poster`) | Working QR code for the request form, PNG download, a printable A4 poster and a copy-link button. It automatically uses an address a phone can reach. |
| **Demo** (`/demo`, `/guide`) | Employee and operator role switch (clearly labelled as a demo), reset with confirmation, storage status, an "about this prototype" section and the presentation guide. |

## Quick start: run the demo on your laptop

You need **Node.js 20.9 or newer** (version 22 LTS is recommended).

1. Install Node.js from <https://nodejs.org> (choose "LTS"). Restart your computer afterwards on Windows.
2. Get the code. On GitHub, open the repository → **Code** → **Download ZIP**, then unzip it. Alternatively, run `git clone` and check out the branch.
3. Open a terminal in the `woodmillflow` folder:
   - **Mac:** open Terminal, type `cd ` (with a space), drag the `woodmillflow` folder onto the window, and press Enter.
   - **Windows:** open the `woodmillflow` folder in File Explorer, click the address bar, type `cmd` and press Enter.
4. Install once (this takes a few minutes and needs internet):

   ```bash
   npm install
   ```

5. Start the demo:

   ```bash
   npm run demo
   ```

   This builds the app and starts it. The terminal then shows:

   ```
   Laptop:  http://localhost:3000
   iPhone:  http://192.168.1.23:3000   (same Wi-Fi or Personal Hotspot)
   [QR code]
   ```

6. Open `http://localhost:3000` on the laptop.

Orders are saved in `woodmillflow/.data/pglite` and survive restarts. On first start the database fills itself with ten fictional sample orders.

To start it again later without rebuilding, run `npm run demo:start`. To stop it, press **Ctrl + C** in the terminal.

## Open it on your iPhone

The laptop runs the server, and the iPhone connects to it over the network. **Both devices see the same orders**, because orders are stored on the server, not in the browser.

**Most reliable method: the iPhone's Personal Hotspot.** This avoids company or guest Wi-Fi that blocks devices from seeing each other.

1. On the iPhone: **Settings → Personal Hotspot → Allow Others to Join** (switch on).
2. On the laptop: join the iPhone's Wi-Fi network.
3. Start the app with `npm run demo`, or restart it if it was already running, so it shows the new address.
4. Scan the QR code shown in the terminal, or on the laptop's **QR Code & Poster** page, with the iPhone **Camera** app. Then tap the link.

If both devices are on the same home Wi-Fi, that works too. Use the `iPhone:` address shown in the terminal.

> Use the iPhone's Camera app, not a third-party QR app. Safari opens the request form.

## Hosted deployment (optional): Vercel + Neon

A hosted version gives you an `https://` web address that works anywhere, including on mobile data. This needs free accounts, so it cannot be done for you automatically. Allow about 20 minutes.

1. **GitHub:** make sure this repository (with the `woodmillflow` folder) is on your GitHub account.
2. **Vercel:** sign up at <https://vercel.com> with your GitHub account → **Add New… → Project** → import this repository.
   - **Root Directory:** click *Edit* and choose `woodmillflow`. **This is important.**
   - The framework preset is detected as Next.js. Leave the build settings as they are.
3. **Database:** in the Vercel project, open **Storage → Create Database → Neon (Postgres)**, accept the free plan and connect it to the project. This adds `DATABASE_URL` automatically.
4. **Settings → Environment Variables:** add the following:
   - `DEMO_ACCESS_CODE`: a code only you know, for example `harbour-2026`. Visitors must enter it. The QR code includes it, so scanning still works.
   - `DEMO_RESET_PIN`: a PIN for the Reset Demo button.
   - `APP_URL`: your Vercel address, for example `https://woodmillflow-yourname.vercel.app` (you can add this after the first deployment).
5. Click **Deploy**. When it finishes, open the address, enter the access code, and check the following:
   - **Demo Settings** shows "PostgreSQL server" as the storage.
   - A request submitted on the iPhone appears in the work queue on the laptop.

Notes:

- Without a database, the hosted app shows a clear "database not configured" message. It does not quietly lose orders.
- Any PostgreSQL provider works (Supabase, Neon or another). Set `DATABASE_URL` to its connection string.
- Do **not** deploy to company infrastructure or use real data without IT authorisation.

## Settings (environment variables)

Copy `.env.example` to `.env.local` for local use, or add the values in Vercel. All are optional for a laptop demo.

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` / `POSTGRES_URL` | PostgreSQL connection string. Leave empty to use the embedded database in `.data/pglite`. |
| `APP_URL` | The public address used for QR codes. |
| `DEMO_ACCESS_CODE` | Makes the whole app private: every page needs this code. |
| `DEMO_RESET_PIN` | PIN for Reset Demo. Required for reset when using `DATABASE_URL`. |
| `DEMO_MODE` | `true` by default. `false` disables the role switch, and operator screens then refuse access. |
| `NEXT_PUBLIC_CLOCK_NUMBER_FORMAT` | `numeric` (default) or `alphanumeric`. |
| `NEXT_PUBLIC_CLOCK_NUMBER_MIN_LENGTH` / `_MAX_LENGTH` | Clock-number length rule (default 4–8). This is a placeholder, not a real company format. Rebuild after changing it. |
| `WOODMILLFLOW_DATA_DIR` | Folder for the embedded database (default `.data/pglite`). |

## Resetting the demo data

- **In the app:** go to **Demo Settings → Reset demo data**, type `RESET` and confirm. On a hosted database you also need the `DEMO_RESET_PIN`.
- **Laptop, from scratch:** stop the app, delete the `woodmillflow/.data` folder and start it again. It reseeds automatically.

The sample orders use times within working hours (Monday to Friday, 07:00–17:00 UK time) relative to when you reset. **Reset shortly before presenting** so the newest sample orders show "minutes ago".

## Troubleshooting

| Problem | What to do |
| --- | --- |
| The iPhone shows "Safari can't open the page" | The devices are not on the same network, or the network isolates devices (common on company and guest Wi-Fi). Use the iPhone Personal Hotspot ([see above](#open-it-on-your-iphone)) and restart `npm run demo` so it prints the new address. |
| The QR code points to `localhost` | Open the laptop page using the `iPhone:` address from the terminal, or set `APP_URL`. The QR page warns you about this. |
| Mac asks "Do you want node to accept incoming connections?" | Click **Allow**. |
| Windows Firewall prompt | Allow Node.js on **Private networks**. |
| The terminal says the port is already in use | Another copy is running. Close it, or run with `PORT=3001 npm run demo:start` (Mac) or `set PORT=3001 && npm run demo:start` (Windows). |
| `npm` is not recognised | Node.js is not installed, or the terminal was opened before installing. Reinstall Node.js LTS and open a new terminal. |
| The operator page says "Woodmill operator view" | Tap **Continue as Sam Morgan (demo)**, or use the role switch. |
| The hosted app says the database is not available | `DATABASE_URL` is missing in Vercel. Connect Neon or Supabase ([see above](#hosted-deployment-optional-vercel--neon)) and redeploy. |
| Everything else | Run `npm run check` and read the first error. |

## How it is built

- **Next.js 16 (App Router) + TypeScript + Tailwind CSS 4.** The UI components follow shadcn/ui patterns (Radix Dialog, `class-variance-authority`) with Lucide icons.
- **React Hook Form + Zod.** One shared schema validates in the browser and again on the server.
- **PostgreSQL** through a small adapter:
  - **PGlite**: PostgreSQL compiled to WebAssembly, stored on disk. It is used for laptop demos and tests, and needs no installation.
  - **postgres.js**: used for any real PostgreSQL server (`DATABASE_URL`).
  - Both run the same SQL schema, with check constraints, foreign keys, unique indexes and transactions.
- **Polling with SWR** (every 4–5 seconds) keeps the work queue and tracking pages up to date across devices.
- **`qrcode`** generates the QR codes in the browser and in the terminal.

```
woodmillflow/
├── src/app/                 pages (employee, operator, tracking, QR, guide, demo) and API routes
├── src/components/          UI (request form, operator dashboard, tracking view, shared UI)
├── src/lib/                 shared domain rules, validation, UK date formatting, config
├── src/server/              database adapter, schema, seed data, order service, sessions
├── src/proxy.ts             optional private-demo access gate
├── scripts/demo.mjs         laptop demo launcher (prints addresses and a QR code)
├── tests/                   unit + integration tests
├── e2e/                     Playwright end-to-end tests
└── docs/                    presentation guide, IT brief, test results
```

### Data model

| Table | Key fields |
| --- | --- |
| `users` | id, clock_number (unique), name, role (`employee` / `operator`), department |
| `departments`, `production_lines` | configurable lists (active flag, sort order) |
| `orders` | id, reference (unique, `WM-YYYY-NNNN`), requester, department, production line, hull reference, date required, submitted_at (UTC, set by the database), status, requested priority (+ reason), approved priority, notes, tracking_token (unique, random), idempotency_key (unique) |
| `order_items` | id, order_id (cascade), position, material category and description, thickness/length/width (mm), quantity, grain direction, cutting requirements (array), drawing reference, notes |
| `status_history` | id, order_id, event type, previous/new status, changed_at, changed_by, comment, internal flag |
| `order_sequences` | per-year counter used to generate references atomically |

## Security notes

What the prototype already does:

- All input is validated on the server. Size limits and control-character stripping apply, and database constraints act as a second layer.
- Tracking links use 192-bit random tokens. Order references cannot be used to look up orders.
- Operator internal comments and the operator's name are removed before data is sent to the tracking page.
- Status changes follow fixed transition rules, use row locks, and detect conflicting updates from two devices.
- Duplicate submissions are prevented by an idempotency key and a unique constraint.
- Operator APIs require the operator role. Write APIs require JSON and reject cross-site origins.
- The app sends security headers (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`) and asks search engines not to index it.
- An optional access code makes a hosted demo private. The reset PIN is compared in constant time.
- No credentials are stored in the code. Configuration comes from environment variables.

**The demo role switch is not authentication.** It exists only so one presenter can show both views. Before any real use, the following would be needed:

- company sign-in (for example Microsoft Entra ID)
- role-based permissions enforced on the server and in the database
- IT-approved hosting
- a data-retention policy
- audit and logging requirements
- a security review and a privacy assessment

Alternatively, an existing approved platform could be used instead.

## Known limitations and future enhancements

**Limitations (by design for a proof of concept):**

- There is no real sign-in. The role switch is a demonstration device, and `DEMO_MODE=false` locks the operator screens.
- Anyone can submit a request with any fictional clock number. Clock numbers are not checked against an HR system.
- There are no push or email notifications. Pages update by polling every 4–5 seconds.
- File and drawing uploads are not implemented; only a drawing reference number is recorded. There is no CAD integration.
- Departments and production lines are database tables, but there is no admin screen to edit them yet.
- There are no management reports or CSV export, which were deferred to keep the core workflow reliable.
- "My requests" relies on tracking links saved in the browser on that device, plus the demo employee's orders in demo mode.
- The laptop demo works only while the laptop is on and connected to the same network as the phone.
- The app has been tested in Chromium at iPhone sizes. **It has not been tested on a physical iPhone or in Safari by the developer.** Check it on your own iPhone before presenting.

**Possible future enhancements, if a pilot were approved:**

- enterprise sign-in and permissions
- integration with existing company systems
- Teams or email notifications
- drawing attachments with access controls
- an admin screen for departments, lines and the material catalogue
- reporting on the pilot measures (see the IT brief)
- CSV export
- offline queueing for areas with poor signal
